# Functional Design — Preview Platform Simulators

**Depth**: Minimal — this is a rendering feature with no domain model, no persistence, and no
business rules in the usual sense. Following the precedent set by this repo's previous feature
(`construction/audit/functional-design/post-type-taxonomy-analysis.md`), the design is captured
as one focused document rather than the full business-logic / domain-entities / business-rules
artifact set, which would be empty ceremony here.

**Scope**: the three decisions the execution plan flagged as worth settling before coding —
(D1) how simulators reuse already-inlined assets, (D2) deterministic engagement counts,
(D3) post→surface routing — plus the frontend component hierarchy (D4), which the stage rules
require when a unit includes UI.

---

## D1 — Asset reuse: build the simulator from the review feed's own DOM

**The constraint.** `requirements.md` NFR-2: the Q3_2026 preview is ~10 MB, essentially all of it
base64 image bytes inlined as data URIs. Re-rendering five new surfaces (IG Feed, IG Profile, IG
Reels, Facebook, TikTok) by emitting `<img src="data:...">` again would multiply that.

**What the page emits today, per row:**

| Surface | Encoding emitted | Note |
|---|---|---|
| Review card — image | 800 px JPEG data URI | |
| Review card — carousel | 520 px JPEG per slide | |
| Review card — video | 720 px poster frame | |
| **IG Grid cell** | **340 px JPEG data URI** | **a second, independent encoding of the same asset** |

That last row matters: the existing IG Grid already duplicates every Instagram asset at a smaller
size. It is pure duplicated weight in the current 10 MB.

**Decision.** The simulator does **not** emit any image bytes. It is constructed **at runtime in
the browser** by cloning the review feed's existing media nodes:

```
node = document.querySelector('.card[data-rowid="IG-014"] .media')
clone = node.cloneNode(true)     // copies the src STRING; the file holds the data URI once
```

`cloneNode` duplicates the DOM node's `src` attribute — a reference to the same string already in
the document. No additional bytes land in the HTML file. The simulator then wraps each clone in
platform-specific chrome generated by JavaScript.

**Consequence — the file should get smaller, not bigger.** FR-3 removes the standalone IG Grid,
and the IG Profile tab clones the same full-size media nodes scaled down by CSS
(`object-fit: cover`) instead of using separate 340 px encodings. Dropping those thumbnails
removes real bytes. `_ImgCache.save()` already prunes entries not requested during a run, so the
340 px cache entries fall out on the next build too.

**Net expectation**: output size **decreases**. NFR-2's "under 15% growth" becomes a ceiling we
expect to beat comfortably. This is a prediction to be **measured** at Build and Test, not
assumed — the same discipline the repo's `LINK_STYLES` table was built with.

**What Python must add to support this** (metadata only — no image data):
1. `data-rowid` on each `.card` article, so JS can locate a row's media node. (`.gcell` already
   carries one.)
2. A compact `SIM_POSTS` JSON array emitted once into the page: one entry per row with
   `row_id, platform, date, day, status, format, is_reel, is_carousel, handle, caption,
   hashtags, hook, asset_link, kind, engagement{...}`. Captions and hashtags are already in the
   document, but re-stating them as data is far simpler than scraping them back out of card
   markup, and the text cost is negligible against a 10 MB baseline.

**Rejected alternative.** Emitting each data URI once into a JS registry (`IMG = {id: "data:…"}`)
and having *both* the review feed and the simulator reference it by key. This would also satisfy
NFR-2, but it requires refactoring the review feed's rendering as well, enlarging the blast
radius of a change whose whole appeal is that it is confined to new code. Cloning achieves the
same byte count with no change to existing output.

## D2 — Deterministic engagement counts

**Requirement.** FR-10: plausible invented counts; deterministic per Row ID; consistent across
every surface a post appears in.

**Decision.** Compute in **Python**, once per row, and ship the result inside `SIM_POSTS`.
Computing server-side (rather than in JS) buys three things: the numbers are identical across
surfaces by construction; the function is a pure Python function and therefore unit-testable
under the Partial PBT setting; and the JS stays presentational.

**Algorithm** — `engagement(row_id, platform, post_type) -> dict`, pure and total:

1. Hash the Row ID with **FNV-1a (32-bit)** — a few lines, no dependency, stable across Python
   versions and platforms (unlike `hash()`, which is salted per process and would produce
   different numbers on every run).
2. Derive independent uniform draws from disjoint bit-slices of the hash.
3. Map each draw onto a plausible band for the platform and post type:

| Platform / type | Primary metric | Secondary |
|---|---|---|
| Instagram feed image / carousel | likes | comments ≈ 2–8% of likes · saves ≈ 3–10% |
| Instagram Reel | views | likes ≈ 4–9% of views · comments ≈ 3–7% of likes |
| Facebook post | reactions | comments ≈ 4–12% · shares ≈ 2–6% |
| TikTok | views | likes ≈ 5–10% of views · comments · shares · bookmarks |

Secondary metrics are derived **from** the primary draw, so a post never shows more comments than
likes — the kind of incoherence that makes a mockup look broken.

4. **Relative timestamp** ("2h", "3d", "1w") is computed from the row's Date against the
   calendar's latest date, so the newest post reads as recent and older posts age plausibly
   down the feed. Undated rows get no timestamp.

**Invariants** (the PBT targets):
- Determinism — same `row_id` ⇒ same output, across processes and runs.
- Coherence — `comments <= likes`, `likes <= views` where views exist; all values non-negative
  integers.
- In-band — every value falls inside its declared band for the platform/type.
- Totality — never raises, for any string row_id including empty or non-ASCII.

**Question 1 — what scale should the numbers suggest?**
This is the one thing I cannot derive from the code, and it changes how the mockup feels.

A) **Emerging account** — tens to low hundreds of likes, a handful of comments. Reads honestly
for an account that is still growing.

B) **Established account** — low thousands of likes, hundreds of comments, tens of thousands of
Reel/TikTok views. Reads like an account with reach.

C) **Aspirational** — high thousands to six figures. Makes the feed look like a big brand.

X) Other (please describe after [Answer]: tag below)

*Default if you skip this: **A** — an emerging account. It is the least likely to feel jarring
against a calendar for an account that is still being built, and it's a one-line constant to

## D3 — Post → surface routing

**Decision.** A single ordering rule and five membership rules, all derived from fields the
reader already produces. No new sheet columns, no new classification logic.

**Ordering (FR-4)** — every surface, identically:
1. Date descending (newest first).
2. Rows with a blank or unparseable Date sort last.
3. Ties broken by Row ID descending, so ordering is stable between builds.

**Membership**:

| Surface | Rule |
|---|---|
| Instagram · Feed | `platform == instagram` — all formats |
| Instagram · Profile | `platform == instagram` — all formats, 3-column grid |
| Instagram · Reels | `platform == instagram` **and** `_is_reel(job)` |
| Facebook | `platform == facebook` |
| TikTok | `platform == tiktok` |

`_platform_key()` and `_is_reel()` already exist and are reused unchanged — `_is_reel` keys off
the Format column, which is the sheet's own categorization, so the Reels tab and the review
page's existing "Reels" chip agree by construction (an FR-6 acceptance criterion).

**Status filtering (FR-5)** is applied on top of membership at render time, reading the same
`flt.s` state the review chips already drive. One filter state, two consumers — the simulator
cannot drift out of sync with the chips.

**Empty surfaces**: a tab whose membership is empty under the current status filter shows a
neutral "No posts match the current filter" panel inside the phone, not a blank device.

## D4 — Frontend component hierarchy

```
#sim                        overlay root, hidden until opened
├── .sim-top                overlay header (outside the phone)
│   ├── .sim-close          × button — also bound to Esc and backdrop click
│   ├── .sim-tabs           Instagram · Facebook · TikTok (with per-tab counts)
│   ├── .sim-status         compact mirror of the status filter  [ASSUMPTION-1]
│   └── .sim-chassis        chassis on/off toggle
└── .sim-stage
    └── .phone[data-chassis="on|off"]
        ├── .phone-notch        device notch / dynamic island
        ├── .phone-status       time · signal · wifi · battery
        └── .app[data-platform] platform application chrome
            ├── .app-top        IG wordmark / FB blue bar / TikTok "Following | For You"
            ├── .app-body       the scrolling surface (see below)
            └── .app-nav        bottom tab bar
```

`.app-body` contents by platform:

| Platform | `.app-body` |
|---|---|
| Instagram | sub-tabs **Feed · Profile · Reels** → `.ig-feed` (post list) / `.ig-profile` (header + 3-col grid) / `.ig-reels` (snap-scroll 9:16) |
| Facebook | `.fb-feed` — post list, caption above media |
| TikTok | `.tt-feed` — snap-scroll 9:16, one post per viewport, right action rail, bottom caption block |

**State** (a single JS object, no framework):

```
simState = {
  open:     false,
  platform: 'instagram',      // active tab
  igTab:    'feed',           // feed | profile | reels
  chassis:  true,             // FR-7 toggle
  built:    {}                // surface key -> true, so each surface renders once
}
```

Status filter is **not** duplicated into `simState` — it stays in the existing `flt.s` so the two
views cannot disagree (FR-5).

**Interaction flows**:
- **Open** — Simulator chip → `#sim` shown, body scroll locked, Instagram Feed built lazily on
  first view. Review feed stays mounted underneath (it is the source of the cloned nodes, so it
  must not be destroyed).
- **Close** — ×, `Esc`, or backdrop → overlay hidden, body scroll restored. Because the review
  feed was never unmounted, scroll position and filters are inherently preserved (FR-1).
- **Switch platform / IG sub-tab** — build that surface if `built[key]` is falsy, then show it.
- **Change status filter** — invalidate `built`, rebuild the visible surface, refresh tab counts.
- **Toggle chassis** — a data-attribute flip on `.phone`; pure CSS, no rebuild.
- **Hover a post** (FR-9) — reveal `.sim-meta` (Row ID · date · status dot) via CSS
  `:hover`/`:focus-within` on the post wrapper. Absolutely positioned, so no layout shift.
- **Play a video** (FR-8) — poster + play button; on click, swap in a Drive player iframe
  **lazily** (never pre-mount ~100 iframes). See below.

**Lazy building** matters: constructing five surfaces × 120 rows up front would stall the page on
open. Each surface builds on first view only.

## D5 — Video playback mechanism (ASSUMPTION-2, to be verified)

**Planned primary**: Drive's own player in an iframe —
`https://drive.google.com/file/d/<file_id>/preview` — injected on click, replacing the poster.
`file_id_from_link()` in `core/drive.py` already extracts the id from the sheet's asset link; no
new Drive call and no permission change (the file is already link-shared).

**Why not `<video src>` against a Drive URL**: the repo's `exporters/__init__.py` link-style
table records that `lh3` serves a *poster JPEG* for videos rather than the mp4, and `uc` returns
an empty 303 body — both fail silently. `download` does serve real bytes with the right
content-type and may work in a `<video>` tag, but it is a redirect-following fetch of a
large file with no extension. The iframe player sidesteps all of it by letting Google serve its
own player.

**Fallback (FR-8)**: if `navigator.onLine` is false, or the iframe reports no load within a short
timeout, the post keeps today's behaviour — poster frame plus a play button linking to the clip
on Drive in a new tab. Degradation must be silent; a broken embed frame is worse than no embed.

**This must be measured during Code Generation**, in all three contexts the page runs in: a local
`file://` open, the Drive-hosted copy, and the Apps Script web app (whose sandbox is the most
likely to block a third-party iframe). If the Apps Script context blocks it, the fallback is the
answer there rather than abandoning inline playback everywhere.

## D6 — Non-regression surface (FR-11)

The simulator is **additive**: new markup, new CSS classes, new JS, all namespaced under `sim`/
`phone`/`app`. It touches existing behaviour in exactly two places, both deliberate:

1. **IG Grid removal** — the `grid` chip, the `#grid` section, and the `_grid_cell` call site in
   `build_preview`. `_grid_cell` itself is retained and reused by the IG Profile tab.
2. **`data-rowid` added to `.card`** — a new attribute; nothing reads `.card` attributes today
   except the existing filter code, which keys off `data-platform`/`data-status`/`data-reel`/
   `data-carousel`.

Untouched: `applyFilter`, the carousel binder, `copyText`, `onStatusChange`, `hydrateStatuses`,
`showViewer`, `initLive`, the back-to-top/current-week widget, and every Apps Script handler.

**Question 2 — carousel behaviour inside the simulator.**
Cloned carousel nodes arrive with their slide track but without the JS bindings (arrows, dots,
scroll sync), which are attached per-element at page load.

A) **Rebind** — run the existing carousel binder over the clones so they swipe exactly like the
review feed. Most faithful; a few extra lines.

B) **First slide only** — the simulator shows slide 1 with the "1/N" badge, matching how a
carousel appears in a real feed before you swipe.

X) Other (please describe after [Answer]: tag below)

[Answer]: 

*Default if you skip this: **A** — rebind. A carousel you cannot swipe undersells the format, and
the binder is already written and generic over `.media.carousel` elements.*
